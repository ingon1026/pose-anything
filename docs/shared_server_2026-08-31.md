# 공유 서버(DGX Spark) 운용 — 2026-08-31

지금까지 이 저장소는 **1인 1기계**(RTX 4070 Ti · WSL2) 전제로 쓰였다.
DGX Spark 은 **여러 명이 같은 기계를 쓴다.** 그래서 바뀌는 것만 적는다.

> **이 문서에서 Spark 실측은 아래 다섯 줄뿐이다.** 나머지는 전부 *"재야 한다"* 다.
>
> ```
> aarch64 · NVIDIA GB10 · 드라이버 580.95.05 · CUDA 13.0 · Python 3.12.3
> nvidia-smi --query-gpu=memory.total → [N/A]      ← 통합 메모리(CPU·GPU 공유)
> ```

---

## 1. 통합 메모리 — 저장소의 VRAM 서술이 그대로 안 통한다

GB10 은 CPU·GPU 가 메모리를 공유한다. `nvidia-smi` 가 **총량조차 못 낸다**(위 실측).
저장소의 VRAM 서술은 두 종류이고 **깨지는 것은 둘째뿐**이다:

| | 예 | Spark 에서 |
|---|---|---|
| **절대 사용량** | ② 7,411 · ④ 9,784 · SAM3 몫 2,373 MiB · Isaac 2,641 · 1008 의 +178 | 값이 다를 뿐 **양은 정의된다.** 재측정 대상 |
| **총량이 분모인 파생값** | `12GB 대비 여유` 3,413 / 2,697 · `남는 여유` 2,498 / 3,591 / 2,265 · `9,784 / 12,282 = 79.7%` · 8/18 의 `81%` | **분모가 없다.** 다른 기계 값이 아니라 **계산 자체가 성립하지 않는다** |

**수치는 지우지 않았다** — 전부 RTX 4070 Ti 에서 유효하다. 각 자리에 어느 기계
값인지 조건을 붙여 뒀다([image_size](image_size_2026-08-21.md) ③ ·
[isaac_sim_stability](isaac_sim_stability_2026-08-14.md) "VRAM 내역").

⚠ **이게 저장소의 OOM 위험 모델을 통째로 건드린다.**
[isaac_sim_stability](isaac_sim_stability_2026-08-14.md) 의 결론은
*"위험한 것은 절대 사용량이 아니라 **재할당이 일어날 만큼 여유가 없는 것**"* 이다.
**Spark 에서는 그 여유를 못 잰다.** 8/18 의 "81% 인데 CUDA 에러 0 건" 같은 판단
기준을 그대로 옮기면 안 된다 — **무엇으로 여유를 볼지부터 다시 정해야 한다. 미확인.**

## 2. `scripts/measure_vram.sh` 는 Spark 에서 그대로 못 쓴다

**코드는 안 고쳤다.** 돌리기 전에 이걸 알고 있어야 한다.

- **파생값이 성립하지 않는다.** `sample()`(`:21-29`)이 읽는 것은
  `nvidia-smi --query-gpu=memory.used` 다. **`memory.used` 가 GB10 에서 무엇을
  세는지는 안 재봤다** — 확정된 것은 `memory.total` 이 `[N/A]` 라는 것뿐이다.
  총량이 없으니 이 스크립트의 출력으로 **"남는 여유" 를 계산할 수 없다.**
- ⚠ **`teardown()`(`:31-36`)이 남의 노드를 죽인다.**
  `pkill -f "roboworld_perception/perception_node"` 는 `run.sh:49-51` 과 같은
  **도메인을 안 보는 pkill** 이다(§3). 공유 서버에서는 **VRAM 을 재는 것만으로**
  같은 계정의 남의 인식 노드가 죽는다.
- **남이 GPU 를 쓰면 그 몫이 섞여 들어온다.** 기존 측정은 1인 1기계 전제였다.
  재측정할 때는 **기계를 혼자 쓰는 창을 잡을 것.**

## 3. `ROS_DOMAIN_ID` — 혼자일 땐 선택, 여럿이면 필수

**격리 방법·확인 절차·함정은 [docs/README.md](README.md) "냉시동 검증" 절의 격리
표에 이미 다 있다. 거기를 읽어라.** 여기엔 **여럿이 쓸 때만 달라지는 것**만 적는다.

- **각자 다른 `ROS_DOMAIN_ID` 를 배정할 것.** 안 걸면 남의 bag·남의 Isaac 브리지와
  같은 토픽 이름으로 섞이고 **에러 없이 출력이 전량 폐기된다**(격리 표 "잊으면
  보이는 것" 행). 저장소는 도메인을 아무 데도 안 걸어준다 — **매 셸에서 손으로.**
  `77` 은 격리 표가 실행으로 검증한 값이라 **이미 임자가 있는 번호로 보고** 배정할 것.

⚠ **그런데 도메인은 `pkill` 을 못 막는다 — 이것이 공유 서버에서 남을 죽인다.**
`run.sh` 는 시작할 때(`:49-51`)와 끝날 때(`:63`)
`pkill -f "roboworld_perception/perception_node"` 를 **무조건** 돌린다. 도메인은
DDS 계층이고 pkill 은 프로세스 계층이라 서로 못 막는다(2026-08-28 실측, 격리 표).
**사정거리는 계정이 가른다**:

| 실행 경로 | 어느 uid 로 도나 | 남의 인식 노드가 죽나 |
|---|---|---|
| **같은 계정을 공유** (공용 계정으로 각자 로그인) | 그 공용 uid | **죽는다.** 도메인을 아무리 나눠도 못 막는다 |
| **계정이 다름** | 각자 uid | **못 죽인다.** `pkill` 이 다른 사용자의 프로세스에 권한이 없어 조용히 넘어간다 |
| `docker compose run` | **non-root** — `docker-compose.yml` 의 `user:` 키가 `${UID:-1000}:${GID:-1000}` 를 건다 | ~~그 uid 소유 노드만~~ → **못 죽인다.** uid 와 무관하게 PID 네임스페이스가 막는다(아래 2026-08-31 실측) |
| `docker run` / `Dockerfile` 직접 | **root** — `Dockerfile` 에 `USER` 선언이 없다 | ~~죽을 수 있다~~ → **못 죽인다.** root 여도 마찬가지다(같은 실측) |

→ **각자 다른 계정을 쓰는 것이 도메인 배정보다 먼저다.** 공용 계정이면
`run.sh` 를 동시에 못 쓴다고 보는 것이 맞다.

**확인됨 (2026-08-31 실측) — 컨테이너 안의 `pkill` 은 호스트 프로세스에 못 닿는다.**
`docker-compose.yml` 은 `network_mode: host` · `ipc: host` · `privileged: true` 를
선언하지만 **`pid: host` 는 선언하지 않는다.** 그래서 PID 네임스페이스가 분리돼
있고, 컨테이너는 호스트 프로세스를 **아예 못 본다**:

```
조건: docker run --network host --ipc host --privileged   (pid:host 없음 — compose 와 같음)
호스트 PID 573 개 · 컨테이너가 보는 PID 4 개(전부 자기 것)
호스트에 띄운 더미: 컨테이너에서 "안 보임" · pkill -f 결과코드 1(대상 없음) · 더미 생존
```

→ **위험한 것은 컨테이너 경로가 아니라 호스트에서 직접 도는 `run.sh` 다.**
`run.sh` 는 `source install/setup.bash` 로 **호스트에서** 도는 스크립트이고,
그 `pkill`(`:49-51`, `:63`)만이 남의 노드에 닿는다. **사정거리는 위 표의 첫 두 행
(계정)이 전부 가른다.**

⚠ **이 기계에서는 계정이 갈려 있다 — 확인함.** `k3i` 그룹(gid 1000)에
**7 명**(`ai_dev` `ingon` `cho` `dspark` `minsu` `sby317` `ykkkim`)이 각자 uid 로
들어 있다. 표의 **"계정이 다름" 행이 적용되므로 호스트 `run.sh` 의 `pkill` 도
서로 못 죽인다.** 공용 계정으로 갈아타지만 않으면 된다.

## 4. 파일 소유권 — 바인드 마운트에 남의 uid 파일이 쌓인다

`volumes:` 의 바인드 마운트(`./bags` · `./output` · HF 캐시)에 컨테이너가 쓴 파일은
**호스트에 컨테이너 uid 소유로 남는다.** 공유 서버에서는 **다음 사람이 그걸 지우지도
덮지도 못한다.** 실제로 계속 쌓이는 곳은 `output/` 이다. 경로마다 다르다:

- **`docker compose run` — 이미 막혀 있다.** `docker-compose.yml` 이 `user:` 키로
  `${UID:-1000}:${GID:-1000}` 를 건다. ⚠ **다만 기본값이 문제다** — 같은 파일의
  주석이 적어둔 대로 `UID` 는 bash 내부 변수라 export 되지 않고 `GID` 는 bash 에
  아예 없어서, 그냥 두면 **경고 없이 항상 `1000:1000`** 이 된다. 공유 서버에서
  uid 1000 은 **많아야 한 명**이고, 나머지 사람은 자기 것도 root 것도 아닌
  **uid 1000 소유 파일**을 받는다.
  ⚠ **이 기계에서 uid 1000 이 누구인지 확인했다 — 실재하는 공용 계정 `k3i`**
  (`k3i:x:1000:1000:...:/home/k3i`)다. 즉 `.env` 를 안 쓰면 **모두의 파일이 `k3i`
  계정 소유로 쌓인다.** 참고로 이 작업 계정 `ingon` 은 **uid 1008** 이라 기본값이
  자기 uid 인 사람은 **7 명 중 아무도 없다**(§3 의 그룹 명단). → **`.env` 는
  선택이 아니라 필수다.** → **넘기는 방법 두 가지가 그 주석 블록에 있다
  (`.env` 또는 `UID=$(id -u) GID=$(id -g) docker compose ...`). 거기를 읽어라.**
  RealSense 라이브 경로가 이 줄로 깨지는 것도 같은 주석에 적혀 있다.
- **`docker run` / `Dockerfile` 직접 — 여전히 root 다.** `Dockerfile` 에 `USER`
  선언이 없다. 이 경로로 돌리면 `--user $(id -u):$(id -g)` 를 손으로 붙여야 한다.

⚠ **확인됨 (2026-08-31 실측) — 소유권을 고치는 그 조치가 컨테이너를 깨뜨린다.**
`--user` 로 non-root 를 걸면 **그 uid 가 이미지 `/etc/passwd` 에 없을 때 SAM3 가
import 단계에서 죽는다**:

```
docker run --user 1008:1008 ... -c "from transformers import Sam3Model"
→ KeyError: 'getpwuid(): uid not found: 1008'
  transformers/models/sam3/modeling_sam3.py:29
   → torchvision/__init__.py → torchvision/ops/poolers.py → getpass.getuser()
```

이미지 `/etc/passwd` 에는 **uid 1000(`ubuntu`)만** 있다(확인함). 그래서:

- compose **기본값 `1000:1000` 은 우연히 통과한다** — 노블 베이스의 `ubuntu` 다
- 그런데 위에서 "필수" 라고 한 **`.env`(자기 uid)를 넣는 순간 7 명 전원이 이 오류를
  맞는다** — 이 기계에 uid 1000 인 팀원이 없다(§3 명단)

**해법 — `USER` 를 같이 넘길 것.** `getpass.getuser()` 는 `pwd` 조회 **전에**
`LOGNAME`·`USER`·`LNAME`·`USERNAME` 을 먼저 본다:

```
docker run --user $(id -u):$(id -g) -e USER=$(id -un) -e HOME=/tmp ...
→ getpass.getuser() = ingon · SAM3 import 성공
```

**§7-5 의 SAM3 측정은 전부 이 조합으로 돌렸다.**

✅ **`docker-compose.yml` 을 고쳤고 실행으로 확인했다.**
그 파일의 기존 주석은 이 증상을 *"`HOME` 이 `/` 로 잡혀 `~/.ros/log` 가 막힐 수
있다"* 로 적어 뒀는데 **실제 증상은 그게 아니었다** — 주석이 제안한
`ROS_HOME=/tmp/ros` 로는 안 풀린다. **import 단계라 그보다 앞이다.** 주석도 고쳤다.

**쓰기 권한은 돌았다.** 공유 캐시(`/data/hf-cache`, setgid·그룹 `k3i`)에
non-root(`1008:1008`)로 **3.3GB 를 정상적으로 받아 썼고** 파일이 `ingon:k3i` 로
떨어졌다. 다만 §5 의 권고대로 **읽기 전용으로 공유하면 이 쓰기가 같이 막힌다** —
받는 사람만 쓰기 권한을 갖는 구성이어야 한다.

## 5. HF 모델 캐시 — 한 벌만 두면 각자 다시 안 받는다

경로는 이미 환경변수로 열려 있다. 새로 만들 것이 없다:

- `Dockerfile` — `ENV HF_HOME=/cache/hf`
- `docker-compose.yml` 의 `volumes:` — `${HF_HOME:-~/.cache/huggingface}:/cache/hf`

> 줄번호 대신 키·토큰으로 인용한다 — 두 파일은 지금 arm64 대응으로 움직이는 중이라
> 줄이 밀린다.

→ **공유 위치를 `HF_HOME` 으로 가리키면 끝난다.** 각자 홈에 두면 인원수만큼 같은
체크포인트가 복제된다.

**권장: 읽기는 공유, 쓰기는 관리자 한 명.** 여럿이 동시에 같은 캐시로 받으면
부분 파일·락 경합이 난다. 새 모델이 필요하면 관리자가 한 번 받아 넣는다.

> 규모(참고) — 팀 리드 보고값: **호스트 캐시 43GB**, `facebook/sam3` 몫 **3.44GB**.
> **저장소에서 확인한 값이 아니고 Spark 에서 잰 값도 아니다.**

## 6. GPU 동시 사용 — 재측정이 필요하다

여럿이 동시에 SAM3 를 띄우면 어떻게 되는지 **아무 값도 없다.** §1 대로 기존 VRAM
예산 논의(여유 2,498 MiB, 1008 의 +178 MiB)는 통합 메모리에서 **분모가 없어 그대로
안 통하고**, 그 값들 자체도 **1인 1기계 · Isaac 하나 + 인식 하나** 전제다.

재야 할 것 — **값이 없으므로 목록으로만 둔다. 지어내지 말 것**:

- GB10 에서 `nvidia-smi memory.used` 가 무엇을 세는가 (§2)
- 통합 메모리에서 "여유" 를 볼 지표는 무엇인가 (§1 — 저장소 위험 모델이 여기 걸려 있다)
- SAM3 한 벌의 몫, 그리고 **두 벌 이상 동시**일 때
- Isaac Sim 이 같이 도는 조건

**그때까지 "동시에 몇 명까지 되나" 에는 답이 없다.** 값이 나오기 전에는
**한 번에 한 명이 GPU 작업을 하는 것**을 전제로 잡는 편이 안전하다.

## 7. `sm_121` 경고 — 성능 문제가 아니다 (2026-08-31 실측)

컨테이너를 띄우면 매번 이 경고가 뜬다:

```
Found GPU0 NVIDIA GB10 which is of cuda capability 12.1.
Minimum and Maximum cuda capability supported by this version of PyTorch is (8.0) - (12.0)
```

**결론부터 — 기본 설정에서 PTX JIT 은 안 걸린다. 이 경고에 드는 비용은 0 이다.**
경고 문구는 `torch/cuda/__init__.py` 가 자기 `arch_list` 의 최대치(12.0)와 장치
(12.1)를 비교해 내는 **범위 검사일 뿐**이고, 커널이 어디서 오는지는 안 본다.

### 7-1. 왜 그런가 — cubin 이 그대로 로드된다

```
torch 2.10.0+cu130
arch_list  ['sm_80','sm_90','sm_100','sm_110','sm_120','compute_120']
capability (12, 1)
```

`sm_121` cubin 은 **없다.** 그래서 "PTX(`compute_120`)로 JIT 돌겠거니" 라고 읽기
쉬운데, **그게 아니다.** CUDA cubin 은 같은 major 안에서 **minor 상방 호환**이라
`sm_120` cubin 이 `sm_121` 장치에 그대로 올라간다. PTX 는 안 쓰인다.

### 7-2. 근거 — 2×2 대조 (JIT 허용/금지 × 컴퓨트 캐시 켬/끔)

**측정 조건**: DGX Spark · GB10 · 드라이버 580.95.05 · CUDA 13.0 ·
`ingon1026/pose-anything:1.3.0-arm64` · **조건마다 컨테이너를 새로 기동해 5 회**,
중앙값. SAM3 가중치 없이 **torch·cuBLAS·cuDNN·SDPA 커널의 첫 실행 비용만** 잰
것이다 — **SAM3 추론 시간이 아니다.**

| 첫 실행 (ms, 중앙값) | 캐시 켬 | 캐시 끔 |
|---|---|---|
| **JIT 허용**(운용 기본) | matmul 274.4 · conv 53.6 | matmul 67.8 · conv 53.2 |
| **JIT 금지**(`CUDA_DISABLE_PTX_JIT=1`) | matmul 264.6 · conv 49.0 | matmul 71.5 · conv 51.1 |

**행을 비교하라 — JIT 을 금지해도 값이 안 변한다**(274.4 → 264.6, 67.8 → 71.5;
둘 다 실행 간 산포 안). 그리고 **금지해도 그냥 돈다** — 커널이 PTX 를 필요로 했다면
로드가 실패했을 것이다. 두 번째 실행부터는 모든 조건에서 0.3~0.9ms 로 같다.

**JIT 이 실제로 걸리면 어떤 모습인지**(`CUDA_FORCE_PTX_JIT=1`, 같은 5 회):

```
conv#1 14,467.9 · sdpa#1 6,960.2 · interpolate#1 5,860.1 · layernorm#1 4,023.4
gelu#1 3,343.2 · ctx+alloc 1,899.3 · vit_layer#1 268.1      합계 ≈ 36.9 초
```

→ **JIT 은 걸리면 놓칠 수가 없다.** 기본 설정은 그 근처도 안 간다.
bf16 결과값도 네 조건 전부 fp32 대비 최대오차 0.500 으로 같다.

### 7-3. 열의 차이(≈200ms)는 JIT 이 아니라 캐시 기구다

§7-2 표에서 실제로 움직이는 축은 **캐시 켬/끔**뿐이고, 그 차이는 JIT 을 금지한
상태에서도 그대로다 — 그러므로 PTX 컴파일 비용이 아니다. 확인 사살로,
**컴퓨트 캐시는 JIT 을 금지해도 똑같이 쌓인다**: 1 회 실행 후 `CUDA_CACHE_PATH` 크기가 **JIT 허용 194.5MB /
JIT 금지 194.5MB** 로 동일하다. **이 캐시는 JIT 산출물이 아니다.**

⚠ **`CUDA_CACHE_DISABLE=1` 로 200ms 를 줄이지 마라.** 이 탐침이 건드린 커널에
JIT 이 안 걸린다는 것뿐이고, CUDA 는 모듈을 지연 로드(`LAZY`)해서 **안 건드린
커널은 확인된 바가 없다.** 그중 PTX 만 있는 것이 있으면 캐시를 끈 순간 그 JIT 이
**매 실행 반복**된다. 200ms 를 아끼려다 초 단위를 무는 쪽이 될 수 있다.

### 7-4. 그래서 torch 를 올릴 이유가 되나 — 안 된다

경고를 없애자고 `torch 2.10.0` 핀을 건드리면 **저장소 측정 조건 전체가 라벨을
잃는다**([README](README.md) §5). 위 표대로 **얻을 성능이 0** 이므로 지금은 근거가
없다. 경고는 뜨는 대로 두고, 이 절을 가리키면 된다.

### 7-5. SAM3 실측 — 여기서도 JIT 은 0 이다

**측정 조건**: DGX Spark · GB10 · 드라이버 580.95.05 · CUDA 13.0 ·
`ingon1026/pose-anything:1.3.0-arm64` · `HF_HOME=/data/hf-cache`(공유) ·
**노드 기본값**(`image_size=0` → **1008px** · `score_threshold=0.4` · bf16) ·
입력 **720×1280 합성 이미지** · 프롬프트 `물통`(→`thermos`) ·
**기계를 혼자 쓰는 상태** · **컨테이너 신규 기동 3 회, 중앙값**.

**로드**

| | 값 |
|---|---|
| 첫 실행 — **3.44GB 다운로드 포함** | 106.3 초 |
| **캐시 후** (n=3) | **2.38 초** (2.37~2.39) |
| 내역 | import 1.25 · `from_pretrained`→cuda 0.91 · processor 0.22 |
| 모델 | 840.4M 파라미터 · bfloat16 · `model.safetensors` **3,439,938,512 B** |

> §5 의 "`facebook/sam3` 몫 3.44GB"(팀 리드 보고값, 저장소 미확인)가 **Spark 에서
> 확인됐다.** 다만 같은 절의 "호스트 캐시 43GB" 는 여전히 다른 기계 값이다 —
> **이 기계에는 오늘 받기 전까지 HF 캐시가 하나도 없었다.**

**추론** — `Sam3Detector.detect()` 를 한 프로세스에서 6 회 연속 호출

| `detect()` | 기본(운용 조건) | `CUDA_DISABLE_PTX_JIT=1` |
|---|---|---|
| **#1** | 935.9 ms | 938.1 ms |
| **#2~6** | 348.8 ms | 349.4 ms |
| **1회차 초과분** | **587.1 ms** | **588.7 ms** |

**JIT 을 금지해도 초과분이 587 → 589ms 로 그대로다 — 1회차 초과분에 PTX JIT 은
0 이다.** §7-2 의 결론이 SAM3 경로에서도 그대로 성립한다. 남는 587ms 는
cuDNN·cuBLAS 알고리즘 선택 · 지연 모듈 로드 · 할당자 워밍업, 그리고
`sam3_detector.py` 의 `_text_cache` 가 채워지는 첫 텍스트 임베딩이다.

⚠ **RTX 4070 Ti 의 4.1초(단독)와 나란히 놓지 말 것.** 시간 정의만 같고
(`transformers` import 전부터 계산) **기계도 CUDA 층도 다르다.** 같은 표에
넣지 않는 이유는 [README](README.md) §5 와 같다.

⚠ **합성 이미지라 검출이 0 건이다.** `post_process_instance_segmentation` 비용은
검출 수에 비례하므로 **실제 장면은 이보다 느리다.** 위 값은 **인코더 경로 기준**
이고, 검출이 있는 장면의 `detect()` 시간은 **미확인**이다.

### 7-6. 이 절이 확인하지 **않은** 것

- **검출이 있는 실제 장면의 `detect()` 시간** — 위 ⚠ 참고. 마스크 후처리·NMS 를
  거의 안 탔다. torchvision NMS/ROI 커널은 그래서 **여전히 미확인.**
- **open3d 경로**(자세 추정·점군) — 이 절은 검출까지만 봤다. **미확인.**
- **지연 로드(`CUDA_MODULE_LOADING=LAZY`)로 안 건드린 커널** — §7-3 의 주의와 같다.
- **여럿이 동시에 쓸 때** — §6 그대로 값이 없다.

### 7-7. 덤으로 확인된 것 — `docker run` 은 root 소유 파일을 남긴다 (§4)

§4 가 "`docker run` 직접 경로는 여전히 root" 라고 적어둔 것이 **오늘 실행으로
재현됐다.** `-v` 로 붙인 캐시 디렉터리에 **`uid 0` 소유 · `drwx------`** 로
194.5MB 가 쌓였고, **호스트 사용자가 읽지도 지우지도 못했다**(지우는 데 컨테이너를
한 번 더 띄워야 했다). 공유 서버에서 컴퓨트 캐시를 공유 경로에 두면 **먼저 돌린
사람 것만 남고 뒷사람은 손도 못 댄다.** `--user $(id -u):$(id -g)` 를 붙이거나
캐시를 각자 홈에 두는 쪽이 맞다.

## 8. 정확도 — arm64 에서 값이 달라지나 (2026-08-31 실측)

**결론: 안 달라진다.** 결정론적인 부분(풋프린트)은 x86 과 **0.04mm** 차이로 맞고,
확률적인 부분(평면·두께)의 차이는 **실행 간 변동 안**이다.

### 8-1. 측정 조건

```

bag  bags/isaac_belt_moving  (md5 a7a03d7b2925d9c8bd402a4cbd706d2a, 4.47GB,
     color 2768 / depth 2769, 26.1Hz — 정답이 있는 유일한 bag)
run_offline.py --prompts "blue bar with holes" --image-size 0(=1008)
               --detect-interval 1 --max-per-prompt 10 --max-frames 500
반복 21 회 · 매 회 컨테이너 신규 기동 · 기계를 혼자 쓰는 상태 · 3,505 행/run
```

**왜 21 회이고 왜 매번 새 컨테이너인가** — 근거는 저장소에 이미 있다:
[README](README.md) §5 *"std 는 재현성이 아니다"* 와
[belt_plane](belt_plane_2026-08-21.md):204. 요지만 옮기면, 평면은 실행당 한 번만
맞춰 영구 캐시되므로(`_plane_tried`) **프로세스를 새로 띄워야 변동이 나오고**,
`±0.40mm` 가 `repeats=21` 값이라 **회수가 다르면 분포끼리 비교가 안 된다**
(적게 돌리면 폭이 좁게 나와 *"arm64 가 더 안정적"* 으로 오독된다).

**`--max-frames 500`** 은 기준값이 **500 프레임** 측정이기 때문이다(루트
`README.md`:89). ⚠ **그때의 `detect_interval` 은 어디에도 안 적혀 있다** — 이
저장소가 회귀 게이트에서 이 bag 에 쓰는 값인 **1** 로 맞췄다. 조건 하나가
문서에 없는 상태로 비교한 것이니 그만큼은 감안할 것.

### 8-3. 판정 — arm64 문제가 아니다

**결정적인 것은 풋프린트다.** 길이·폭은 평면 맞춤을 안 타서 **실행 간 산포가
정확히 0** 이다(21회 전부 같은 값). 즉 **잡음에 숨을 곳이 없는 결정론적 비교**인데
x86 과 **0.04mm** 차이다. arm64 의 수치 연산이 틀어졌다면 여기서 먼저 드러난다.

평면·두께의 차이(+0.180 / +0.154)는 **실행 간 변동 안**이다 — 두께 σ 가 0.286mm
이므로 차이는 **0.54σ**, 전폭(±0.500)의 3분의 1이다. **잡음과 분리되지 않는다.**

**산포도 같다.** arm64 전폭이 평면 ±0.450 · 두께 ±0.500 으로 기준 **±0.40mm** 와
같은 자릿수다. **더 안정적이지도 불안정하지도 않다.**

**조건이 갈릴 자리도 다 확인했다** — `dist_thresh` 21/21 이 3mm(기준과 같은 가지),
`image_size` 1008, inlier 0.502 대 0.513.

### 8-4. 정지 장면(`isaac_belt`)에서도 같은 답이 나왔다

먼저 `isaac_belt`(정지)으로 21회를 돌렸는데, **그 bag 은 color 78 장 중 4 장만
depth 와 짝이 붙어**([datasets](datasets.md):30) 4 프레임·12 행/run 뿐이었다.
표본이 달라 정본으로 쓰지 않지만, 값은 같은 자리를 가리킨다:

| | 정지 (4프레임) | 움직임 (500프레임) | 기준 |
|---|---|---|---|
| 평면 오차 | +1.420 | +1.520 | +1.34 |
| 두께 오차 | +2.019 | +2.124 | +1.97 |

**두 bag 이 독립적으로 같은 결론을 낸다.**

⚠ **기준값의 출처를 한 번 짚어 둔다 — `+1.97` 은 움직이는 장면 값이다.**
정지 장면 값으로 오해되어 *"움직임이 새 변수로 붙는다"* 는 반론이 한 번 나왔는데,

### 8-5. 확인하지 **않은** 것

- **중심·RPY** — 치수(길이·폭·두께)와 평면만 봤다. `check_accuracy.py` 로 기준 CSV 와

- **open3d 경로 전체** — 자세 추정·점군은 이 절이 안 봤다
- **실기 bag**(test2/test4) — 정답이 없어 arm64 판정에는 못 쓴다

## 9. `docker compose` 경로 — 세 군데를 고쳤다 (2026-08-31)

**이 파일을 이 기계에서 처음 실제로 돌려봤다.** 세 개가 걸렸고 셋 다 고쳤다.
고치기 전에는 **`docker compose up` 이 arm64 에서 시작조차 못 했다.**

### 9-1. `image: latest` 가 amd64 전용이었다

```
docker manifest inspect ingon1026/pose-anything:latest → linux/amd64 하나뿐
1.3.0        → 있음 (amd64)
1.3.0-arm64  → Hub 에 없음 (아직 푸시 안 함)
```

→ `image:` 를 `${IMAGE_TAG:-latest}` 로 바꾸고 `.env` 에 `IMAGE_TAG=1.3.0-arm64`
를 둔다. **x86 쪽 기본 동작은 안 바뀐다.**

⚠ **`pull_policy: missing` 은 답이 아니다 — 넣었다가 실측하고 되돌렸다.**
이 파일 주석의 *"소스를 고쳐도 Hub 이미지가 조용히 돈다"* 를 그걸로 막을 수
있을 것 같지만, **기본값과 동작이 같다**(Compose 2.40.0, 2026-08-31 실측):
로컬에 이미지가 있으면 둘 다 레지스트리에 안 가고, 없으면 둘 다 받으려다
실패한 뒤 빌드한다. **절감 0회.** 레지스트리 접촉을 진짜로 없애려면
`pull_policy: build`(매 `up` 마다 빌드 그래프를 돈다) 뿐이다.

⚠ **`IMAGE_TAG` 는 임시 방편이다.** 아키텍처는 기계가 이미 아는 사실인데 그걸
사람이 `.env` 에 적게 한 것이라, `.env` 를 x86 기계로 들고 가면 거기서 깨진다.
**옳은 해법은 멀티아치 매니페스트다** — `1.3.0-arm64` 를 Hub 에 올린 뒤
`docker buildx imagetools create -t …:1.3.0 …:1.3.0-amd64 …:1.3.0-arm64` 로 묶으면
`image:` 가 한 줄로 돌아가고 `IMAGE_TAG` 도 이 안내도 사라진다. **푸시를 아직
안 해서 지금은 못 한다**(§9-5).

### 9-2. `USER`·`HOME` 이 없어 SAM3 가 죽었다

**기전과 해법은 §4 에 있다.** 여기서는 그 해법을 `environment:` 에 `USER` 와
`HOME` 두 줄로 넣었다는 것만 적는다.

⚠ **compose 에만 넣은 것이라 `docker run`·k8s·CI 경로는 여전히 죽는다**(§9-5).

### 9-3. DDS 설정은 이미 있었다 — 다만 `docker run` 에는 없다

`FASTDDS_BUILTIN_TRANSPORTS`·`RMW_IMPLEMENTATION` 은 compose 에 **원래 들어 있다.**
문제는 **`docker run` 으로 직접 돌릴 때**다. 오늘 라이브 재생에서 실제로 걸렸다 —
`camera_info`(작음)는 오는데 **이미지(큰 메시지)가 에러 없이 안 왔다.** 그 두 줄을
붙이니 `RGB-D input healthy` 로 바뀌었다. **카메라를 붙이면 같은 자리에서 걸린다.**

### 9-4. 확인 방법과 결과

```
docker compose config                    → image 1.3.0-arm64 · user 1008:1008
                                           USER=ingon · HOME=/tmp · pull_policy missing
docker compose run --rm perception \
  python3 scripts/run_offline.py ...     → 4 frames · dist_thresh=3mm inlier=0.512
                                           트랙 6개, docker run 결과와 일치
ls -l output/                            → ingon:ingon — 본인이 지울 수 있다
```

대조로, **`--user` 없는 `docker run` 은 여전히 `root:root` 를 남긴다**(확인함).
`docker run` 경로를 쓸 때는 `--user $(id -u):$(id -g) -e USER=$(id -un) -e HOME=/tmp`
를 손으로 붙여야 한다.

### 9-5. 남은 것

- **`network_mode: host`** — compose 는 호스트 네트워크를 쓴다. 여럿이 동시에
  ROS 를 띄우면 §3 의 도메인 배정이 그대로 필요하다. **오늘은 혼자 썼다.**
- **RealSense 라이브 경로** — 같은 파일 주석대로 `user:` 줄이 카메라를 깨뜨린다.
  카메라가 없어 **확인 못 했다.**
- ⚠ **compose 밖 경로는 아직 안 고쳤다 — 이 절의 수정은 절반이다.**
  `docker run`·k8s·CI 로 띄우면 §9-2 의 uid 오류도, §9-3 의 DDS 누락도 그대로다.
  지금은 사용자가 `-e` 로 손으로 붙이게 되어 있는데 **그게 옳은 깊이가 아니다.**
  근본은 이미지 층이다 — `docker-entrypoint.sh` 가 두 경로 공통의 `ENTRYPOINT`
  이므로, 거기서 (a) `getent passwd $(id -u)` 가 비면 `/etc/passwd` 에 한 줄 추가,
  (b) `source /ws/scripts/ros_env.sh` 를 하면 **양쪽이 동시에 덮이고 compose 의
  사본도 지울 수 있다.** 이미지 재빌드가 필요해 이번에는 안 했다.
